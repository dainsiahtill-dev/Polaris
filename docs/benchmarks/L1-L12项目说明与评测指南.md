# L1–L12 项目说明与评测指南

题库内容修订：`2026-10-22-rich-prompts-1`。

本轮目的是让 120 个项目提供不同的工程挑战和不同的需求表达，测出 Polaris 是否真正理解需求、实现核心机制并交付可用产品。本文是内部评测指南；题库更新与组件测试通过均不代表项目已经通过真实 Bench。

运行时题库以 [projects_v2.json](../../src/backend/scripts/factory_bench/projects_v2.json) 为准。逐题的提示词、表达形态和评测说明见 [项目提示词全集](L1-L12项目提示词全集.md)。默认 runner 仍读取这个文件；`projects_v1.json` 与独立的 pelican 题库保持原样。

## 本次调整

原目录已有 120 个题目、12 个等级、7 种主语言和 110 个 `project_type`，题材覆盖游戏、音乐、科学创意、工具和互联网平台。但多数 `brief` 只有“用某语言实现某标题”的同段改写，`test_focus` 也几乎只复述创意钩子。名目丰富不等于实际任务丰富：如果输入输出、交互、状态变化和错误场景都不明确，模型很容易交付相似的命令行壳或固定 JSON。

本次保留全部项目 ID、等级、标题、主语言、领域和原 `checks`，逐项重写需求与测试重点，替换空泛的 novelty 标签。提示词采用不同的来信、委托、玩法、实验、交互走查、接口需求、故障演练、审计或发布验收形式。各题的信息顺序和语气随任务变化，不要求相同开头或相同五段结构。

公共需求文档只补充运行、源码、真实验证与原工程下限。它不要求模型填写合同、业务 hash、覆盖关系、CE 蓝图或 `target_files`；也不因语言或分类强行把所有题改为网页或命令行。项目内明确的交付形态优先。

## 丰富度要看什么

| 维度 | 需要覆盖的差异 | 容易造成虚假丰富度的做法 |
| --- | --- | --- |
| 用户入口 | 浏览器操作、终端交互、可播放媒体、离线分析、服务接口、真实多客户端 | 所有题最终只打印 JSON |
| 核心机制 | 图算法、约束调度、资源守恒、交易、排序推荐、媒体生成、状态机、协议与事务 | 只改实体名称，复用同一个 CRUD |
| 状态与时间 | 无状态计算、持久化、固定步长、回放、并发冲突、重启恢复 | 把一次函数调用说成实时系统 |
| 输入材料 | 表单、文本、地图、音符、事件流、数据集、配置和多客户端操作 | 只有硬编码的“演示成功” |
| 质量风险 | 边界、误输入、权限、重复事件、数据损坏、恢复、可访问性、性能 | 只有编译或截图，没有结果断言 |
| 需求表达 | 用户来信、玩法规则、实验卡、工作流、接口请求、审计和故障剧本 | 只更换段落标题或给同模板贴风格标签 |

同一等级内应比较不同形态；同一形态也应跨等级比较。主语言分布保持为 TypeScript 18、JavaScript 17、Python 19、Go 17、Rust 17、C++ 16、Java 16。语言平衡与题材数量只是描述性统计，不是对任务难度或通过率的证明。

## 等级与工程挑战

以下是本轮写作的难度组织，不是新增平台前置流程。实际项目须同时满足自身需求和既有工程深度下限。

| 等级 | 主要挑战 | 应观察的质量差异 |
| --- | --- | --- |
| L1 | 单个可运行闭环、简单交互或模型 | 输入真的改变结果，错误可理解，核心规则可测试 |
| L2 | 状态、文件与一组关联操作 | 保存重开正确，非法操作不破坏已有状态 |
| L3 | 算法与模块组合 | 可达性、边界、确定性和领域规则同时成立 |
| L4 | 跨组件交互与多条用户流程 | 页面/终端/服务与核心逻辑一致，操作有真实反馈 |
| L5 | 领域交易与持久化边界 | 资源、库存、版本和提交结果一致，失败不半写 |
| L6 | 多会话或多个子系统共享状态 | 真实客户端/子系统相互影响，重复输入不重复结算 |
| L7 | 复杂约束、调度与可解释分析 | 冲突和不可行情况有原因，不能只返回一个分数 |
| L8 | 系统耦合、重放与恢复 | 中断、回放、编辑和重开后规则仍成立 |
| L9 | 跨模块一致性与来源追踪 | 结果可以追溯，局部操作不破坏其他模块的约束 |
| L10 | 多阶段编排与故障处理 | 失败传播、恢复点、重试和重复操作有明确语义 |
| L11 | 可测规模与性能边界 | 在声明负载下测量正确性和成本，报告实际机器与条件 |
| L12 | 综合系统与关键不变量 | 多场景、多用户或恢复压力下仍满足核心系统性质 |

“3A”“MMO”“操作系统”类标题均按题内说明实现有界的本地原型，不承诺商业规模。原型仍须保留题目核心机制，不能把多人缩成单循环模拟、把物理缩成随机日志、把事务缩成无冲突的字典读写。

## 如何判断完成质量

先检查本题是否真的交付，再比较完成得好不好。功能缺失、结果错误或验证未执行，不能用美观程度、文件数或模型回复补成通过。

| 质量维度 | 观察方法 |
| --- | --- |
| 功能正确 | 逐项执行本题明确的操作与验收例子；增加一个未在示例中出现的同类输入，排除硬编码 |
| 产品可用 | 从 README 启动，通过实际入口完成用户流程；网页检查操作反馈与空态/错误态，CLI 检查参数、输出与退出码 |
| 领域深度 | 改变关键参数、顺序或约束，检查结果是否按领域规则变化，而非只换文字 |
| 状态可靠 | 按本题需要执行保存重开、并发、重复事件、中断或恢复；检查数据是否丢失、重复或越权 |
| 工程质量 | 源码组织与入口一致，依赖可安装，配置不是空壳，测试覆盖真实业务结果 |
| 媒体与交互 | 声音文件可解码且参数影响内容；可视化反映真实状态；多人操作经真实连接传播 |
| 交付效率 | 记录墙钟时间、真实物理请求和已知用量、修复次数、人工介入；未知费用保留 UNKNOWN |

可为适用维度记 0–4 的辅助质量分：0 为缺失或错误，1 为仅有演示外观，2 为主流程可用但关键边界不足，3 为主流程和关键边界均有证据，4 为在此基础上还有清楚的恢复或额外质量证据。这个分数是人工/独立 QA 的分析口径，本次未把它实现成自动评分器，也不替代平台验收。

不适用的维度记 N/A 并说明原因，不把无界面工具扣成 UI 失败，也不让没有音频要求的题补交声音。对比总分时使用相同适用维度与权重；平台 accepted、独立质量发现与人工复核结论分别保留。

## 题型的真实验证

- 浏览器题：必须从界面触发核心行为，核对操作前后状态和错误反馈。漂亮首页、静态截图和按钮存在均不足以证明功能。
- 多人题：按题目要求打开多个独立客户端，连接同一个服务，实际发送有先后或冲突的操作；观察同步、重连与权限。循环调用两个用户对象只能证明局部逻辑。
- 音乐/声音题：检查 WAV/MIDI 或实际声音路径，验证时长、节拍、声部或事件与输入一致。无声环境可以解析文件，不把未听过写成听感通过。
- 模拟题：使用固定种子、固定步长或可重放输入，检查资源/范围等不变量，再改变参数验证敏感性。题目中的教学近似不能冒充真实科学精度。
- 协议/数据库题：用两个会话或故障序列检查隔离、重复、冲突和恢复；只验证正常提交不足以证明事务正确。
- 大规模题：声明数据量、客户端数、事件数、硬件和测量方法；报告真实数值，不把题目负载或期望速度写成已测性能。

项目题内需要的长连接、轮询或事件协议由目标项目需求决定；Polaris 自身的实时控制面仍遵循统一 runtime.v2 WebSocket 规则。不能把平台规则无差别套进目标项目，也不能让目标项目污染平台代码。

36 题阶段在每级额外选两题，使该级同时覆盖不同语言和不同交付形态；不要只挑已成功或依赖最少的题。完整报告必须列出所有计划样本、实际样本、跳过原因和失败，不能把选中的成功样本当作全题库结论。

比较 Polaris 版本或协作方式时，固定题库修订、模型绑定、权限、工具、运行预算和环境；同一题多次运行使用新的隔离工作区。先报告逐题结果和质量缺口，再聚合成功率。若评估表达形态的影响，需要为相同语义准备配对版本；本题库同时改变了需求具体度和表达方式，不能单独归因为“某种写法更好”。

本轮不启动 Bench、不调用真实模型、不修改既有生成项目、不回填历史验收。后续正式执行仍使用已有内部 runner、显式 host/LLM 配置、`isolated` 实例和独立 QA，单题 5400 秒、外层 6000 秒预算保持原样。支持的参数以 runner 的 `--help` 为准。
