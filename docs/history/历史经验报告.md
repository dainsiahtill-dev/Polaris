## 1. 先读结论：项目真正积累了什么

### 1.1 十条最值得带走的经验

1. 一次故障先找真实状态拥有者，再修它的合同；调用方、投影、缓存不能替拥有者造事实。
2. 模型输出、工具执行、真实副作用、持久收据、任务完成、项目接受、资源释放分别证明。
3. 分析模型问题，先看该次最终 provider request；完整消息、实际工具集合、参数、身份和物理发送证据必须相互对应。
4. 调用先归一化，再逐项授权。上下文里的文件名不产生写权限，显式空写范围仍然是空。
5. 守卫正确也可能被错误的输入合同误导；必须验证请求准备、回调执行和恢复路径使用同一调用的实际合同。
6. “安全拒绝”与“能够恢复”都要成立；更强的阻塞并不自动带来更好的交付能力。
7. 修复写入成功只证明补丁生效；复测与当前输入绑定才说明对应缺陷真的消失。
8. 失败证据不能改成缺失，未知不能记成零，进程停止不能冒充逻辑资源已释放。
9. 单元测试、联合回归、独立审阅、发布门禁、全新原生交付是递进证据，不能相互代替。
10. 一轮只解决一个可证伪的通用根因。留下反例、旧失败、源码版本和未验证范围，才能减少下一轮重走弯路。

### 2.2 第一轮反复：目录统一了，权威未必统一

早期统一 CLI、编排内核和状态投影，旨在解决入口分叉问题。随后 Cell 与 KernelOne 尝试把能力归属、依赖、允许副作用和公共合同固定下来。但把文件搬到新目录、保留一层兼容 facade，并不等于所有实际调用都消费了新合同；旧读法和旁路仍可能存在。

从这一阶段起，“implemented”与“adopted”必须分列。今天同样适用：一个公共 DTO 已定义、一个 Cell 已列入图谱，不等于默认角色链路、冷恢复路径和真实产物都已验收。[S004 · L1—15](../../src/frontend/public/reports/polaris-history-sources.html#s004-l1)；[S004 · L127—139](../../src/frontend/public/reports/polaris-history-sources.html#s004-l127)；[S004 · L224—234](../../src/frontend/public/reports/polaris-history-sources.html#s004-l224)；[S004 · L381—387](../../src/frontend/public/reports/polaris-history-sources.html#s004-l381)

### 2.3 第二轮反复：看到了上下文，不等于模型收到它

3 月底的 ContextOS 与工具审计暴露出“组件存在、日志漂亮、实际未接入”的问题。4 月转向事务提交、控制面与上下文数据面隔离。此后，审计对象从 prompt、messages 摘要逐步推进到最终 provider request，再进一步要求物理发送路径、尝试身份和可读取快照。

这不是术语升级：工具可能在 slim、retry、provider 转换或恢复 bootstrap 中丢失；若只检查上游 RoleProfile 或 UI，就会把平台裁剪错误误判成模型能力不足。

### 2.4 第三轮反复：修复能力增强了，也制造了新的权威问题

多语言确定性修复让平台可以处理编译器、manifest、模块拓扑等可重复错误。但同时出现风险：在 adapter、Factory、QA 或 Bench 各补一条规则，修复路径越多，越难保证同一权限、同一收据、同一复测。

因此 repair kernel 收敛到 `director.runtime`，跨 Cell 消费 public 合同。扩展必须先查语言槽位、catalog 与 coverage，经历诊断、计划、组合、策略执行、收据和复测。规则元数据、预留槽位、可执行绑定是三种不同状态。[S005 · L105—112](../../src/frontend/public/reports/polaris-history-sources.html#s005-l105)

### 2.5 第四轮反复：历史成功没有消除系统性失败

8 月首证值得保留；它说明特定版本、特定项目曾有真实结果。9 月底再梳理时，材料又明确承认缺少当前版本的连续、多项目、无外部修复验证。一次成功的价值，在于提供可研究的样本；不能靠改标题让它承担尚未验证的通用性与经济性。

10 月采用更清楚的模块研发方法，但新原生样本仍不断暴露 producer/consumer、权限、当前性、QA 身份、命令语法和资源收尾交接问题。最有价值的变化，是开始把每个失败归属到具体边界，并保留已有成功的有限范围。[S001 · L1—38](../../src/frontend/public/reports/polaris-history-sources.html#s001-l1)

## 3. 历史真正沉淀下来的架构原则

### 3.1 角色链路与责任

任务运行链路必须经过 `PM → Chief Engineer → Director`。PM 给合同，CE 给可接受的蓝图与交接，Director 在获准范围内产生效果，Verifier 和 QA 提供各自证据。不能因 CE 缺少投影就让 Director 直连，也不能由 QA、测试脚本代替执行者修目标项目。

Architect、Scout、Resident 或外部审阅可以帮助研究和建议，但不能被悄悄升格成事实拥有者或验收签发者。外部子代理审阅是工程协作证据，不是产品运行依赖。[S005 · L61—76](../../src/frontend/public/reports/polaris-history-sources.html#s005-l61)

### 3.2 一个事实拥有者，多个可重建视图

| 对象 | 可以说明什么 | 不能代替什么 |
| --- | --- | --- |
| owner 原始事件与提交 | 该拥有者实际承诺的事实 | 其它 owner 的成功、整个项目接受 |
| effect receipt | 某次受权效果、内容 hash 与执行身份 | 未执行的效果、缺失复测、全项目正确性 |
| Run Ledger / TaskBoundary | 受明确版本和输入绑定的聚合判断 | 模型自述、任意旧 completed 状态 |
| ContextOS / UI | 该范围内可观察到的上下文和运行投影 | 写权限、真实 wire、完整账单 |
| Instance Registry / Launcher | 实例发现、端口、进程与运维入口 | PM/CE/Director/QA 的交付事实 |
| Job Token | 从控制面派生的执行能力范围 | 第二套任务事实、上下文自行授予的权限 |

只读查询不能隐式写回或重建执行权威；缓存或压缩视图不能成为执行真源。跨 Cell 优先复用已有 public 合同和 KernelOne 原语，避免每次故障再造一套分类表、执行器或状态机。

### 3.3 从自然工具习惯到受控效果

正确链路是：工具名与参数归一化、逐项权限与路径门禁、受控执行、效果收据、复测、上层消费。归一化是兼容能力，授权是边界，二者不能互相替代。

同一物理请求中，最终提供给模型的工具集合、callback 可执行集合和恢复路径集合必须一致。对非法调用要明确拒绝并留下证据，不能在授权前根据提示词正则静默删除调用；也不能因为模型在上下文里读到某路径，就把该路径并入写权限。[S005 · L73—74](../../src/frontend/public/reports/polaris-history-sources.html#s005-l73)

### 3.4 上下文必须有身份、当前性与可读取原件

每次真实调用至少核对角色 system 身份、messages、tools、tool_choice、response_format、最终请求 token/窗口占用和关键合同覆盖。`context_snapshot_ref` 应是当前 workspace 下能读到的 24 位 hex 快照 key；不是 request hash、文件路径或日志字符串。

语义快照回答“准备了什么请求”，wire/transport 证据回答“哪个物理尝试实际发送了什么”。审计中不能将二者自动等同，也不能从一次路径完善推导所有路径都已覆盖。[S005 · L77—85](../../src/frontend/public/reports/polaris-history-sources.html#s005-l77)

### 3.5 检测、修复、验证各守一层

Bench gate 是量具；Factory 编排不应偷偷修复产物；修复内核拥有确定性修复语义；实际变更仍需 Director 的策略门禁和收据；Verifier 在固定的当前输入上执行。模型建议可以进入 advisory，但不能覆盖 policy、注册权威规则或签发通过。

不存在“一条更聪明的 regex”可以替代完整修复协议。对大文件优先精确 span/text patch，结构化文件保持结构化合并；fallback、整文件替换和 rollback 必须有理由、前后 hash 和审计结果。[S005 · L105—112](../../src/frontend/public/reports/polaris-history-sources.html#s005-l105)

### 3.6 隔离运行，绑定观察

一个后端进程只绑定一个 workspace。并行项目通过独立实例、独立端口和独立 runtime 组合；实时只走 Nats-JetStream 与 `/v2/ws/runtime`。项目页不能订阅全局 Bench 后被最新 session 切换到别人的 workspace。

默认 runtime 根为 `<workspace>/.polaris/runtime`；旧缓存位置可只读发现，不能自动复制、双写或在活跃运行中切根。主实例、临时实例和 Launcher 控制实例的生命周期边界也必须分开。历史固定 RAM-disk、共享主后端切 workspace 或外置缓存的做法，不能从旧报告直接搬回当前实现。[S005 · L96—103](../../src/frontend/public/reports/polaris-history-sources.html#s005-l96) [S005 · L113—113](../../src/frontend/public/reports/polaris-history-sources.html#s005-l113)

## 5. 历次“通过”分别证明了什么

### 5.1 证据阶梯

| 层级 | 能成立的结论 | 仍缺什么 |
| --- | --- | --- |
| 设计/蓝图/ADR | 目标、边界、应满足的不变量 | 实现、实际接入与运行效果 |
| 静态代码审阅 | 当前代码存在某实现或疑似风险 | 风险是否真实触发、产物是否正确 |
| 组件与反例实验 | 指定输入、版本、替身范围内机制成立 | 相邻接口、真实 provider、完整交付 |
| 联合回归/独立审阅 | 特定合同和相邻消费者得到验证 | 发布后的实际运行与故障恢复 |
| 发布门禁 | 冻结候选满足所执行的检查 | 指定项目真实运行、QA、资源收尾 |
| 单个真实新运行 | 该版本、该任务、该干预范围的结果 | 重复性、多语言覆盖、泛化与成本 |
| 冻结版本的多批验证 | 明确分母下的成功率与失败谱系 | 未覆盖任务域、分布变化与长期成本 |

不能把这些层级的数字相加。新增测试数量不是缺陷数量，一次原生运行中的重复报错也不是多个独立根因。

## 6. 为什么总是补了这里、又坏了那里

### 6.1 反复出现的是边界问题，不只是算法问题

第一类反复来自权威混用：用 UI 读模型恢复执行状态，用文件存在替代收据，用模型 verdict 替代当前 owner 的提交，用实例 registry 替代任务完成。局部逻辑看起来合理，拼起来却有多个不同的“真相”。

第二类来自合同在传递中变形：完整工具清单被提示词过滤，显式空权限被 legacy 默认值填回，当前 owner/session 字段被压缩心跳覆盖，CE 的 artifact/recipe 在 normalizer 中丢失。真正的修复点往往在 producer 与 consumer 之间，不在最后抛异常的函数。

第三类来自验证失配：直接给守卫一个手写列表会绕过错误交接；新建 service 仍命中同进程缓存；构造器被跳过的 test double 没有真实 authority port；负例虽然失败却不是目标故障触发。它们会制造“测试正确、真实链路仍错”的假象。

第四类来自目标与度量失配：为了更快变绿缩短预算、让 gate 修产物、调整分母、把失败写成缺失、用组件测试代替 native。量具一旦和被测对象共同修改，后续成功就失去解释力。

### 6.2 科学模块研发的固定闭环

采用既有约定：理解目标、观察事实、建立基线、研究方案、提出假设、设计实验、实现与验证、分析结果、正式集成、真实验收、积累知识。关键不在步骤名称，而在每一步留下可被下一人推翻或复核的输入和输出。[S006 · L24—61](../../src/frontend/public/reports/polaris-history-sources.html#s006-l24)

| 步骤 | 最少应留下的材料 |
| --- | --- |
| 定义问题 | 症状、第一失败边界、输入/版本、实际 owner、影响范围 |
| 建立基线 | 原始请求与事件、源码 hash、可重复失败、已有副作用与 UNKNOWN |
| 提出假设 | 一个机制解释、相反预测、什么结果会推翻它 |
| 做实验 | 单因素变化、真实 public 接口、正反例、替身与环境边界 |
| 最小修复 | 在真实 owner 内复用既有能力，列明相邻消费者 |
| 验证与独审 | 精确失败码、故障确实触发、冷进程/重放等必要对照 |
| 集成与冻结 | 联合回归、发布门禁、源码/config 指纹、唯一启动者 |
| 正式新运行 | 固定原合同、独立实例、只读观察、无外部目标修复 |
| 分析与归档 | 交付/QA/效果/释放/成本分别判定，旧失败保持不变 |

### 6.3 审计要同时照到哪些地方

每次卡住或准备重跑，至少覆盖：架构链路、角色身份、最终请求、工具归一化与授权、上下文卫生、运行事件、UI workspace 绑定、产物真实门禁、模型健康、问题是否收敛。

这些不是要为每个小改动新建一套大流程。检查强度应随风险调整：普通可逆文档改动不必跑完整 Factory；涉及权限、持久提交、恢复、QA 或资源拥有权时，则需要与相应边界匹配的反例和真实链路证据。

### 6.4 可以并行的研究与必须串行的执行

不同 owner 的只读研究可并行；修改应拆成互斥范围，回收后由主线程重看 diff、源码 hash 与测试。正式运行应在相应候选集成、冻结、获准后由唯一 operator 发起。不能让多个 Agent 共用主后端切换 workspace，或在运行期间修改候选源码。

审阅意见帮助发现问题，却不成为产品事实源。外部工具等待、脚本拼错路径、观察器缺少环境变量，应记为工程执行错误，不能混入模型或平台失败统计。

## 8. 下一阶段：按什么顺序继续才不会重走旧路

这是依据当前检查点提出的后续顺序，不是本次已执行的工作。

1. 按采用的检查点，R11 当前模块已止写，先完成持久化与 request-scope 独立复核。最初 CE 拒绝可能合法，应核对已保存的真实参数及 producer/consumer 合同；无法恢复的旧参数字节继续保留 UNKNOWN，禁止先放宽守卫。
2. 将已确定的模块修改按真实 owner 集成，核对相邻消费者和依赖图；修复、测试、静态分析与源码/config 冻结绑定到同一候选。
3. 按项目已要求的发布门禁取得准入，再对原始 L1-01 合同发起一次全新、正式、隔离运行；只读观察，保留外部干预为零的边界。
4. 对每个真实请求、效果、命令验证、QA、ProjectOutcome 与资源收尾分别取证。失败就保留第一失败和 UNKNOWN，回到所属模块；不靠 host 补装依赖、改命令或写目标文件制造通过。
5. 完成一例后，再证明重复性、受控故障恢复、并发与重启；按明确冻结版本、项目集合、预算、模型与干预政策组织多批实验。
6. 最后讨论通用性与经济性：同合同、同模型、同预算比较，记录完成率、恢复率、真实调用、总时间、账单、人工分钟与安全事件。未知值保留，不用 token 或测试数替代经济收益。

## 10. 最终认识与来源
