# Polaris 底座完善与重构方案 —— 两份第一性推导的合并

2026-11-28 · 合并稿。本文件合并两份独立推导：
- **A**：《Polaris 工程求解平台的底座完善与重构方案》
  （`POLARIS_FOUNDATION_FIRST_PRINCIPLES_20261128.md`，codex 著）—— 10 项底座责任 + 6 阶段实施
- **B**：本会话的根因推导（L0→L8）—— 从两项承诺拆到「开环 / word-vs-deed」

结论：**A 给出"列全"的方法（事实对象 × 生命周期 × 故障条件）与"做多少"的清单；
B 给出"为什么会坏"的根因。两者是同一棵树的两层，不冲突。**

本文件额外给出 **一处排序修正**（见 §4）与 **四条可证伪判据**（见 §5）。

## 1. 从两项客户承诺到三条公理

A 的两项承诺（可分别检验）：

1. 给定目标、约束与授权，**自主产出可运行、可独立验收、可由第三方复核**的产品。
2. 存在可独立求解的工作时，**增加算力能缩短合格交付时间**。

B 把它拆成三条**正交**公理（承诺 1 = A1 + A2，承诺 2 = A3）：

| 公理 | 含义 | 可证伪判据 |
|---|---|---|
| **A1 独立接受** | 验收者与实现者**不同模型 / 不同熔断 / 不同预算 / 不同上下文** | 任一项共享即不成立 |
| **A2 无人介入** | 失败可**自愈或诚实终止**，不需要人 | 失败后无自动恢复且无明确 fail-closed |
| **A3 产物存在** | 实现能在**预算内完成** | 实现阶段无独立预算 |

**承诺 1 决定正确性，承诺 2 决定扩展价值。** 与 A 一致。

---

## 2. 根因树（B 的推导，L0→L8）

```
L0  目标：无人介入 + 独立接受
L1  公理：A1 独立 / A2 自愈 / A3 存在
L2  要求：独立模型、独立熔断、独立预算、强制裁决、FS 有界、工具链可移植
L3  机制缺陷：角色不独立 / 能力未断言 / 验收不是独立阶段
L4  抽象缺陷：执行单元选错（turn 而非 role）/ 环境当成细节 / 没有"证据"概念
L5  第一性：授权-执行 / 策略-能力 / 声明-事实 未分离
L6  共同根：用「约定」代替「机制」
L7  为什么：系统是「开环」的（无自我检验回路）
L8  统一：word（说的）与 deed（做的）未分离 —— 系统把 word 当 deed 用
```

**L8 的三个面孔**（对应 A 的三组责任）：

| 未分离 | word | deed |
|---|---|---|
| 授权 / 执行 | 谁说它可以动 | 它实际动了什么 |
| 策略 / 能力 | 宿主说要做 | 底材实际能做 |
| 声明 / 事实 | 模型说什么 | 宿主观测到什么 |

**一句话根因**：

> **Polaris 是开环系统，没有机制验证"说的"是不是"做的"，只能假设 ——
> 而假设在真实负载下必然失效。**

---

## 3. 三根因 → 十责任映射（A 的清单是根因的投影）

A 的十项责任**不是 10 个独立任务**，而是 3 个根因的投影：

| 根因 | A 的责任 |
|---|---|
| **R1 授权-执行未分离** | 5 规划拆解、7 并行/恢复/隔离、10 开放扩展 |
| **R2 策略-能力未分离** | 2 身份存储生命周期、3 权限工具效果、4 模型上下文知识 |
| **R3 声明-事实未分离** | 1 客户目标与验收、6 算力预算、8 工件证据集成、9 实时观察、（10 部分）|

**推论**：修一个根因，会同时改善多条责任；**按责任平行推进会重复劳动**。

## 4. 排序修正（两份推导的唯一分歧）

| | A 的顺序 | 本合并稿的建议 |
|---|---|---|
| 第 1 步 | **PM/CE 发布全项目计划** | **先闭合验收（word/deed 分离）** |
| 理由 | 有计划，闲置算力才有分配对象 | **验收是当前首要失败模式** |

**实测依据**（本会话，~32 个项目）：

- **17 PASS（53%）**
- 首要失败 = **验收环节**（QA 占位 / 熔断 / provider 超时），**不是**缺计划
- 修复链：角色 client 不分 → 熔断连坐 → invoke 超时 → 裁决要求前置（**已做 5 环，未闭合**）

**第一性论证**：

> **承诺 1（独立接受）未闭合时，承诺 2（加算力）会放大失败。**
> 多 Director 并行 = 更多候选 → 更多验收失败。

**修正后的顺序**：

```
A:   0 固定现状 → 1 项目计划 → 2 领取 → 3 集成 → 4 总控 → 5 收益
合并: 0 固定现状 → 1' 闭合验收(A1) → 1 项目计划 → 2 领取 → 3 集成 → 4 总控 → 5 收益
```

在「固定现状」与「项目计划」之间**插入「验收闭环」**（word/deed 分离 + QA 独立执行单元）。

## 5. 合并实施计划（每批可单独否决）

沿用 A 的「放行证据 / 失败撤回」结构，插入新批次 1'：

| 顺序 | 最小可交付 | 放行证据 | 失败撤回 |
|---|---|---|---|
| **0 · 固定现状** | 列清写入者；冻结源码/配置/权限/样本 | 真实 direct 任务交付 + 中断后效果核对 | 按原始身份修复并复测同一反例 |
| **1' · 闭合验收**（新增）| QA 成为独立执行单元：独立 client / 独立熔断 / 独立超时 / 裁决强制；`accepted` 只能由 `deed` 推出 | 同一候选上：QA 用与 Director 不同的模型与熔断；占位报告被退回；`word` 不能单独推出 `accepted` | 关闭 QA 独立配置，回退共用 Director client（现状）|
| **1 · 全项目计划** | PM 发布带验收场景的目标文档；CE 给全量任务；工程服务发布/保存/查询 | 发布前零项可领；发布后两支线可领、集成受阻；重启同版；重复提交只发布一次 | 关闭新计划准入；direct 按原约定 |
| **2 · 领取与资源** | 任务尝试 + 共享名额 + 隔离实例；幂等与对账 | 抢同任务/同名额/两合格名额/预留崩溃 四组试验 | 停发新尝试，核对在途与名额 |
| **3 · 成果合并** | 版本化成果；集成 Director 采用；独立 QA 验收集成候选 | 局部通过 + 故意不兼容组合都保留；组合失败能定位 | 保留原工件/候选/裁决；选上一已知版本重试 |
| **4 · 接上总控** | 快照 + 推送；上层消费投影；Agent 下钻 | 浏览器从领取跟到释放与 QA；重复/断线/越权不可见 | 关新投影入口，事实写入仍归原 owner |
| **5 · 验证收益** | 单 vs 多 Director；正向/逆向/留出项目 | 两侧独立接受；延迟/费用/失败可第三方复核 | 撤回新调度或选模默认 |

## 6. 四条可证伪判据（替代"感觉更干净"）

| 判据 | 测法 | 现状 |
|---|---|---|
| **闭环存在** | 每次运行都有对自身的观测（卡死/证据/假设）| ⚠️ 看门狗已做；FS 能力未断言 |
| **word/deed 分离** | 结论只引用 `deed`；`word` 不能单独推出 `accepted` | ❌ 未做（`runs.instruction` 与实际指令不一致）|
| **假设显式** | 每条假设是可校验的能力声明，不是默认 | ❌ 未做（drvfs 挂死无事件）|
| **失效可观测** | 假设被击穿**有事件** | ⚠️ 部分（run_stalled 有；provider 超时无）|

## 7. 与现状的差距（本会话实测证据）

**已修并验证**（A1 链，5 环）：
- 角色 client 不分（QA 跑 Director 的模型）→ 修
- QA 熔断参数（5→25，60→15s）→ 修
- QA 熔断器独立命名 → 修
- invoke timeout 30→120s → 修
- 裁决要求前置 + 点名占位措辞 → 修
- 卡死看门狗 + 自动续跑 → 修
- KFS 跨宿主 FS（drvfs）→ 修（POSIX 回退）
- catalog 工具链（Go/Rust/Java + libjli）→ 修

**未闭合**：
- **A1 验收独立预算**（QA 时间被实现挤压）
- **A1 失效可观测**（provider 物理超时无事件）
- **A2 FS 能力断言**（drvfs 硬限制，D 状态不可中断）
- **A3 角色独立执行单元**（授权/预算未分离）
- **word/deed 分离**（`runs.instruction`、占位、`completed≠accepted`）
- **A 的 1 / 2 / 3 / 4 / 5 阶段**（项目计划、领取、集成、总控、收益）

**样本**：~32 → 17 PASS（53%）。**首要失败模式已从"QA 占位"转为"provider 层 + 验收预算"。**

## 8. 第一性结论

1. **A 的 10 责任是对的**（检查矩阵），**B 的 L8 给了根因**（3 根因）。
2. **实施排序应修正**：先闭合验收（承诺 1），再上项目计划（承诺 2）。
3. **四条判据可证伪**，且**每条都对应一个已实测的失败**。
4. **唯一未解的硬限制**：底层 FS 必须可靠（drvfs 不可用）——
   这不是 Polaris 能独自解决的，但**必须变成启动时的显式拒绝**。

**验证整个方案的最终判据**（A 与 B 一致）：

> **L1-L12 全 120 个项目上，独立验收通过率稳定；且失败样本可被第三方复核。**
> 不以单项目结果宣称稳定。
