# Polaris 底座完善与重构方案

2026-11-28 · 合并稿。**Polaris 存在的目的，是把客户想要的各种开发和逆向项目做出来。任务分解的首要价值，是让原本需要轮流完成的工作，可以交给多个 Director 和其他 Agent 同时推进。** 必要支线完成后，正式集成把成果变成一个产品。

本稿沿用两份材料。A 的[十项底座责任与实施蓝图](POLARIS_FOUNDATION_FIRST_PRINCIPLES_20261128.md)提供覆盖检查方法。B 的 L0 至 L8 根因树解释已有失败怎样影响交付。两者共同检验下面这条项目生产链。

## 0. 从客观工作量推导并行分工

**先有产品，才有工作量。** 给定目标、已有资产、可用环境和所需质量，就有必须完成的工作。正向开发包括实现客户行为和接通各部分。逆向项目还要查明目标行为、取得对照和排除错误假设。工作客观存在，拆法由 CE 设计。任务边界和精确工时取决于技术路线、复用程度与新发现。同一个项目，拆成一百张任务卡也可能处处等待。PM 先写清客户目标、已有资料和完成标准。CE 据此列全工作包、交付物和待研究的问题，并给出估算区间和不确定项。

**好的拆解同时回答三个问题。**

| 问题 | 回答 |
|---|---|
| 整个产品还要做什么？ | PM 写清客户目标、已有资料和完成标准。CE 据此列全工作包、交付物和待研究的问题。工作分解结构覆盖必要的调查、研发、验证与最终集成。实验室可以组织同一方向的多项任务。 |
| 哪些工作今天就能同时开工？ | CE 写清每项任务的输入、输出和依赖，并标出写入边界与独占资源。没有现成答案的部分拆成有明确问题、对照和结束条件的研究任务。大型项目先发布覆盖全项目的版本，发现新工作时由 CE 修订受影响的部分。 |
| 再增加一个 Agent，能让客户更早拿到什么？ | 平台将已发布且前置满足的任务，与合适的 Agent、算力、设备、权限、工作区、模型名额和预算匹配。Director 可领实现或研究任务，其他 Agent 按职责领查证、测试或审阅。还有独立支线等待领取时，新增资源就有用武之地。大家都在等同一项上游结果时，优先推进那项工作。 |

**任务粒度取决于能否独立交付。** 一项任务要让执行者凭已给输入开始，又要让下游按约定接收结果。以缩短工期为目的时，重叠执行节省的时间需要超过新增的交接、验证和集成开销。预计耗时最长的依赖链给出工期下界，独占设备还会进一步限制并发。实验室按问题领域组织，Director 的数量随就绪任务和可用算力变化。

以 Spore 为例，可以先固定同一份生物设计、骨架与网格。一位 Director 研究骨骼与 IK，一位使用冻结姿态验证蒙皮，另一位使用固定网格验证涂装。三条支线可以同时推进。新的姿态发布后再做联合验证。所有必要支线完成后，正式集成把成果变成一个产品：集成 Director 接入同一版 Web 创造器，独立 QA 从编辑、涂装、试演一直走到保存重开。PM 在立项时定义的完成标准，到这里用于检验客户能否真正使用它。

工作量按同一基准下各项任务的预计投入汇总，工期则按依赖和可用资源排程。例如 Spore 历史目录登记了 13 个工作包和 77 项任务，其中 14 项没有列出前置，按任务个数计的最长依赖链有 19 项。目录能揭示并行机会，实际工时、资源竞争和本次交付的耗时还要测量。[历史任务图及计算假设](/home/dains/.polaris/research-vision-at3w3hij/task-graph.json)

## 1. 怎样检验交付与加速两项承诺

由上述价值链导出两项可以分别检验的承诺。

1. 给定目标、约束与授权，**自主产出可运行、可独立验收、可由第三方复核**的产品。
2. 存在可独立求解的工作时，**增加算力能缩短合格交付时间**。

B 提出下列三项单次运行的工程条件。A3 说明实现需要足够预算。要证明增加算力缩短工期，还需要可并行的任务、可用资源、成功的集成，以及同范围串行与并行的实测对照。

| 交付条件 | 本批试验的具体做法 | 可观察的失败 |
|---|---|---|
| **A1 独立接受** | QA 独立检查当前候选。B 的资格试验另要求不同模型，并隔离 client、熔断、预算和角色上下文 | 实现者自报直接结算为通过，或物理请求、预算及裁决记录不符合本批隔离约定 |
| **A2 无人介入** | 失败可**自愈或诚实终止**，不需要人 | 失败后无自动恢复且无明确 fail-closed |
| **A3 产物存在** | 在授权预算内形成可运行、可复核的产物 | 只有计划或完成声明，缺少对应产物或正常入口无法运行 |

第一项约束交付质量，第二项衡量并行分工带来的收益。

## 2. 单次交付失效的根因树（B 的 L0 至 L8）

以下保留 B 从验收故障向下追因的原始层次。这里的 L0 是可靠性交付的诊断起点，项目为何需要分工见第 0 节。

```
L0  目标：无人介入 + 独立接受
L1  公理：A1 独立 / A2 自愈 / A3 存在
L2  要求：独立模型、独立熔断、独立预算、强制裁决、FS 有界、工具链可移植
L3  机制缺陷：角色不独立 / 能力未断言 / 验收不是独立阶段
L4  抽象缺陷：执行单元选错（turn 而非 role）/ 环境当成细节 / 没有"证据"概念
L5  第一性：授权-执行 / 策略-能力 / 声明-事实 未分离
L6  共同根：用「约定」代替「机制」
L7  为什么：系统是「开环」的（无自我检验回路）
L8  统一：word（说的）与 deed（做的）未分离 —— 系统把 word 当 deed 用
```

**L8 的三个面孔**（对应 A 的三组责任）：

| 未分离 | word | deed |
|---|---|---|
| 授权 / 执行 | 谁说它可以动 | 它实际动了什么 |
| 策略 / 能力 | 宿主说要做 | 底材实际能做 |
| 声明 / 事实 | 模型说什么 | 宿主观测到什么 |

**B 对所研究失败路径的根因假设**

> 当某条路径仅凭声明推进状态，且没有从实际效果回读时，错误假设就可能被当作完成事实。应按具体路径用反例验证这一判断。

## 3. 三根因 → 十责任映射（A 的清单是根因的投影）

A 的十项责任用于检查平台能力的覆盖面。B 的三个故障根因会横跨多项责任，下表标出相应的排查位置。具体客户项目的任务数量和并行关系由 PM 文档及 CE 拆解确定。

| 根因 | A 的责任 |
|---|---|
| **R1 授权-执行未分离** | 5 规划拆解、7 并行/恢复/隔离、10 开放扩展 |
| **R2 策略-能力未分离** | 2 身份存储生命周期、3 权限工具效果、4 模型上下文知识 |
| **R3 声明-事实未分离** | 1 客户目标与验收、6 算力预算、8 工件证据集成、9 实时观察、（10 部分）|

同一根因由一个负责模块修复，可同时改善多条责任。十项责任用于查漏。实际研发能否并行，取决于任务的输入、交付边界和资源是否独立。

## 4. 产品的因果顺序与当前版本的上线顺序

| 问题 | 产品设计 | 当前版本放行 |
|---|---|---|
| 先解决什么 | **PM 明确项目范围，CE 识别全量工作和可并行支线** | **先用真实单任务证明产物、验证与独立裁决能可靠结算** |
| 为什么 | 可领取的独立任务决定新增算力能投到哪里 | 若当前版本不能稳定区分提交、通过与失败，扩大并发将同时扩大返工与误判的风险 |

**排序依据沿用 B 原稿记录的约 32 个项目样本。**

- **17 PASS（53%）**
- 首要失败 = **验收环节**（QA 占位 / 熔断 / provider 超时），**不是**缺计划
- 修复链：角色 client 不分 → 熔断连坐 → invoke 超时 → 裁决要求前置（**已做 5 环，未闭合**）

工作分解与单任务验收可以同时设计和验证。按 B 报告的故障，正式开放批量领取前，先在固定的代表任务上证明确实能接受合格候选、退回不合格候选。随后用同一份完整计划检验更多 Director 是否带来有效并行。

两种顺序分别回答“为什么需要这些能力”和“当前版本先放行什么”。

```
产品：客户目标 → 盘点必要工作 → 分解任务并标明依赖 → Agent 并行领取 → 成果合流 → 客户产品
放行：0 固定现状 → 1' 单任务验收闭环 → 1 发布完整计划 → 2 领取与资源 → 3 集成 → 4 总控 → 5 实测收益
```

大型项目的第一道调度条件是 PM/CE 已经发布覆盖目标范围的计划。单任务验收闭环是当前版本开放规模化执行的可靠性前置。扩大真实并发前，计划要能指出今天可同时开工的独立支线。其余工作都在等同一项上游结果时，新增 Agent 先用于推进那项上游。

## 5. 合并实施计划（每批可单独否决）

沿用 A 的「放行证据 / 失败撤回」结构，插入新批次 1'：

| 顺序 | 最小可交付 | 放行证据 | 失败撤回 |
|---|---|---|---|
| **0 · 固定现状** | 列清写入者；冻结源码/配置/权限/样本 | 真实 direct 任务交付 + 中断后效果核对 | 按原始身份修复并复测同一反例 |
| **1' · 闭合验收** | 按本批约定为 QA 隔离 client、熔断、执行时间和角色上下文，并把裁决绑定到当前候选 | 同一候选上核对 QA 的实际身份、有效证据及裁决。合格样本能通过，占位报告和不合格样本会被退回 | 停止新策略准入，回到已验证的 QA 配置。在途裁决仍按原候选和证据处理 |
| **1 · 全项目计划** | PM 定义客户目标、范围和完成标准。CE 发布同一计划的工作包结构、任务依赖和工作量估算，注明输入输出、资源与不确定项 | 在约定的两支线样例上，发布前零项可领。发布后可查询哪些任务能同时开工、集成在等谁。漏掉客户要求、循环依赖或不兼容的输入能被发现。重启同版，重复提交只生效一次 | 关闭新计划准入，已发布版本保留可查，direct 按原约定 |
| **2 · 领取与资源** | 空闲 Director 和其他合格 Agent 按能力与权限领取就绪任务，绑定执行尝试、共享名额及隔离工作区 | 竞争同一任务或最后一个名额最多一方成功。两个独立任务和两份合适名额可同时推进。仅有一条上游阻塞其余任务时，空闲 Agent 被导向该上游。预留后崩溃可对账 | 停发新尝试，核对在途任务与名额 |
| **3 · 成果合并** | 版本化成果；集成 Director 采用；独立 QA 验收集成候选 | 局部通过 + 故意不兼容组合都保留；组合失败能定位 | 保留原工件/候选/裁决；选上一已知版本重试 |
| **4 · 接上总控** | 快照 + 推送；上层消费投影；Agent 下钻 | 浏览器从领取跟到释放与 QA；重复/断线/越权不可见 | 关新投影入口，事实写入仍归原 owner |
| **5 · 验证收益** | 单 vs 多 Director；正向/逆向/留出项目 | 两侧独立接受；延迟/费用/失败可第三方复核 | 撤回新调度或选模默认 |

## 6. 四条可靠性判据与一项并行收益对照

表中“现状”沿用 B 的样本记录。具体缺口按运行版本与复测结果更新。

| 判据 | 测法 | 现状 |
|---|---|---|
| **闭环存在** | 每次运行都有对自身的观测（卡死/证据/假设）| ⚠️ 看门狗已做；FS 能力未断言 |
| **word/deed 分离** | 结论只引用 `deed`；`word` 不能单独推出 `accepted` | ❌ 未做（`runs.instruction` 与实际指令不一致）|
| **假设显式** | 每条假设是可校验的能力声明，不是默认 | ❌ 未做（drvfs 挂死无事件）|
| **失效可观测** | 假设被击穿**有事件** | ⚠️ 部分（run_stalled 有；provider 超时无）|

检验平台的扩展价值时，冻结同一份计划、输入、能力与验收条件。先限一个 Director 执行，再开放多个合格执行者和对应空闲算力。记录合格交付总用时、实际重叠的执行、关键路径等待、交接与返工、费用。两边的产品均通过相同验收后，才计算本次加速比。工作包数或已关闭任务数单独无法给出这一结果。

## 7. B 原稿记录的修复与未闭合项

**已修并验证**（A1 链，5 环）：
- 角色 client 不分（QA 跑 Director 的模型）→ 修
- QA 熔断参数（5→25，60→15s）→ 修
- QA 熔断器独立命名 → 修
- invoke timeout 30→120s → 修
- 裁决要求前置 + 点名占位措辞 → 修
- 卡死看门狗 + 自动续跑 → 修
- KFS 跨宿主 FS（drvfs）→ 修（POSIX 回退）
- catalog 工具链（Go/Rust/Java + libjli）→ 修

**未闭合**：
- **A1 验收独立预算**（QA 时间被实现挤压）
- **A1 失效可观测**（provider 物理超时无事件）
- **A2 FS 能力断言**（drvfs 硬限制，D 状态不可中断）
- **A3 角色独立执行单元**（授权/预算未分离）
- **word/deed 分离**（`runs.instruction`、占位、`completed≠accepted`）
- **A 的 1 / 2 / 3 / 4 / 5 阶段**（项目计划、领取、集成、总控、收益）

**样本**：~32 → 17 PASS（53%）。**首要失败模式已从"QA 占位"转为"provider 层 + 验收预算"。**

## 8. 第一性结论

1. **为什么存在。** 为客户开发或逆向重建各种项目。目标一旦确定，就有需要完成、可以调查和估算的工作。
2. **为什么分解。** 拆法由 CE 设计。分解把客观存在的工作变成可分配的独立交付单元。依赖图揭示今天能同时开工的支线，以及必须等待的关键路径。任务卡数量本身不带来并行。再增加一个 Agent 的价值，取决于是否还有独立支线可领。大家都在等同一项上游结果时，优先推进那项工作。
3. **为什么要有平台。** 平台把一份已发布计划匹配到多名 Director、专项 Agent 和不同来源的可用算力，管理领取与交接，并在必要工作完成后正式集成出一个产品。
4. **怎样知道成功。** 在客户的正常使用路径上独立验收集成产品。用同一计划的串并行对照衡量额外算力的收益，再用 L1–L12 的 120 个内部项目检验跨项目稳定性并保留可复核的失败样本。

A 的十项底座责任用于检查上述机制是否齐备，B 的根因树用于定位它们为什么失效。第 7 节的文件系统观测属于具体宿主的可靠性约束，按必需能力探测并记录结果，保持其适用范围。
