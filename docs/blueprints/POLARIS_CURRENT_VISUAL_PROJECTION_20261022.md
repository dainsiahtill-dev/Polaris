# 当前候选图片投影：机制、反例与集成边界

日期：2026-10-22。现有 roles.runtime 内的限定修复，不新增 Cell、控制器、账本或长期记忆。实施前方案与 RED 原件保存在外部审计目录 `task21-current-visual-projection/implementation-plan.md`；本文在集成审查阶段归纳，不回写其时间或历史失败。

## 问题、事实与解释

全新网页 r04 最后一轮在发送模型请求前被本地预算拒绝，用户任务未交付。首个已定位的偏差在 `engineering_visual.build_visual_messages`：它把全部历史浏览器像素重新注入每轮输入，没有按已有当前候选绑定选择。SQLite 保存完整历史是正确行为，派生输入无条件重复所有像素则会阻断继续修复。

原输入 175 条消息、79 对工具调用／结果、42 张图片，其中 38 张可由原 journal 证明属于旧候选。现有结构化估算为 960493，超过当时预算 946720。预算与原生 codec 是不同边界：同一 79 对调用能通过 codec。实际视觉 token、供应商窗口占用和该次 HTTP 发送均不能由语义 prepared 事件推断。

假设是：只在正面证据充分时省略旧候选的派生像素，保留当前证据和全部执行事实，即可让这份输入通过原预算。若生产投影仍拒绝、遗漏当前／引用图片、改变调用／结果／错误或历史 journal，解释与实现即不被接受。它不解释模型为何漏验运动错误，也不声称提升交付率。

## 模块与数据流

```text
EngineeringRunService / 原工程 SQLite（唯一状态 owner）
  当前 review_binding + 同角色 journal + 原始 messages
  engineering_visual：归属核对、完整性验证、非破坏图片投影
  engineering_loop：提交派生请求与辅助选择审计
  KernelOne：原预算准入、原 native codec、真实 provider 请求审计
  模型、合法工具、真实验证与当前独立 QA
```

角色、会话和 workspace 由原 owner 提供。只匹配完整原消息、唯一真实 tool observation、对应 dispatch、唯一 capture 与图片 hash；续跑中复制的相同消息仍须全部位于原 observation 之后。归属或字段不全时保留。比较复用视觉当前性规则，仅忽略 `verification_seq`，其它字段及字段集合都参与；不复制嵌套权限 schema。

省略只作用于派生模型输入中的旧像素。原始图片／事件不变；tool ID、参数、结果、退出码和错误保留，工具结果先于派生图片。当前所有时间／视口图、用户引用图和未知归属图保留。损坏图片即使过期也拒绝，不能靠省略绕开完整性校验。私有显式 host pin 可保留指定图，缺失 pin 明确报错；公共历史比较与取图流程尚未接通。

恢复从原 journal 重建相同投影，不重放工具效果；权限、预算、输出上限、模型配置、codec 与验收标准均未变化。`request_prepared.visual_projection` 记录计数、原因与源事件，不能冒充最终物理请求或另一份权威事实。

独立审查发现首版提前求绑定会阻塞零图片首轮。相邻修正采用延迟求值；只在确有成功浏览器图片需要分类时读取绑定。由原 Verification producer 为特殊输入和观察期间变化提供内部 `ValueError` 子类型，消费者可明确保留未知图片并记录原因，不解析错误文案；权限、身份等错误仍拒绝。实际验收和视觉当前性守卫不随输入投影的容错放宽。修改范围因此包含原 `engineering_verification.py` 的两个观察错误出口。
