# Polaris 科学收敛与渐进重构方案

状态：历史讨论提案，已被本轮用户要求的[完整重构方案](POLARIS_ROLE_AGENT_REFACTOR_20261020.md)取代。不再作为新重构的执行依据；保留原文供追溯。

日期：2026-10-20。依据：《历史经验报告》68 个案例、既有科学研发约定、当前公开合同与本次只读审阅。研究范围是如何提高交付可靠性、恢复能力与可解释性，并控制研究和运行成本。

## 1. 建议与目标

采用**保留 Cell 与 KernelOne、逐条收敛真实交接边界**的方案。以当前正式任务的真实结果决定下一研究点；每次只解决一个有证据的机制，同时减少重复解释、隐式推断和旧消费路径。

过去的材料支持“跨边界合同变形、权威混用和验证失配反复出现”的判断；不能从历史案例直接断言当前源码仍有同样缺陷。因此，本方案首先规定如何发现、证伪与选择改动，再决定是否重构。

目标分四个维度分别衡量：

| 维度 | 要证明什么 | 不能用什么替代 |
| --- | --- | --- |
| 安全性 | 无越权、重复授权、伪造接受和未证明效果的放行 | 拒绝数量、测试数量、其它任务成功 |
| 恢复活性 | 合法状态在明确前提和预算内能前进，或安全终结并说明阻塞 | 所有异常都 fail-closed、无限重试 |
| 交付有效性 | 原合同经过正式链路，产物与必需验证成立，当前 QA 和权威接受可追溯 | HTTP 200、模型返回、工具成功、ledger closed |
| 经济性 | 全部尝试与工程干预的成本能衡量，投入带来可比较收益 | reported tokens、单次成功、未知费用记零 |

安全约束不能被成本或成功率抵消；满足安全后，再比较交付、恢复、延迟和成本。具体成功率、样本量和成本目标应在基线形成后预先声明，不在本方案中虚构达标承诺。

## 2. 为什么选渐进收敛

| 方案 | 短期收益 | 主要代价 | 本次判断 |
| --- | --- | --- | --- |
| 继续逐样例补丁、叠门禁 | 容易推进当前报错 | 重复语义与 false positive 增多，下一边界继续漂移 | 可处理已定位局部错误，不宜作为长期方法 |
| 全面重写底座与状态机 | 可以重新定义结构 | 现有有效防线与恢复语义须重新证明，迁移期间风险最大 | 当前证据不足以支持 |
| 在既有 owner 内渐进替换并切断旧消费 | 能保留有效能力，使改动可比较、可回退 | 必须追完整 producer/consumer 与冷恢复链 | 推荐 |

这是工程选择，不是已做完成本实验的结论；若后续证据表明局部边界无法隔离，应重新评估对应模块的重构范围，而非预设整个系统重写。

## 3. 将 68 个案例压缩成六类研究问题

以下是组织实验的归类，不是独立缺陷数量统计，也不是六个新组件。

| 问题族 | 历史代表 | 待验证的不变量 | 优先改动位置 |
| --- | --- | --- | --- |
| 身份与权限被重新猜测 | 空写权限被补回、task label 与 numeric ID 混用、旧 QA epoch | 身份域明确；当前能力只能由授权 owner 派生；显式空值不当缺省 | 真实 producer/consumer 接口 |
| 同次调用存在多份协议 | offered tools 与 bootstrap 不同、三套 alias/schema、原生调用被预裁 | 规范化和本次工具面由既有唯一来源派生；每个调用都有实际结果或拒绝 | 请求准备与工具交接 |
| 投影替代事实与当前性 | 心跳覆盖会话、热缓存掩盖冷读、预读 head 冒充 CAS | 原始 owner 事实与 UI 投影分离；决定在实际 owner 的原子边界校验版本 | owner 提交与权威消费者 |
| 效果、完成、接受、释放混合 | no-op receipt、suspended 被误读、closed 被当 PASS | 不同生命周期分别证明；失败、缺失、未运行、未知分别保留 | 汇聚 reducer 与 admission consumer |
| 检验没有测到真实机制 | authority 替身、负例错因绿、静态 artifact 假 PASS | 原版本目标机制确实失败；修后合法与非法控制均触发正确边界 | fixture、真实接口实验、独立 oracle |
| 历史与观测成本限制执行寿命 | 巨型 WS 帧、事件累计上限、多个 runtime 根 | 读取工作预算、留存寿命、实时摘要分别设计；存储根由现有 owner 统一解析 | 原存储/投影 owner，按证据选择 |

## 4. 架构应怎样收敛

### 4.1 延续既有职责，不设万能总控对象

运行链路仍是 `PM → Chief Engineer → Director`，后接各自的 verifier 与 QA 证据。KernelOne 提供通用技术原语，Cell 拥有工程语义；跨 Cell 通过现有 public 合同协作。

收敛的重点是减少同一个字段或事实的重新解释次数：

- 原合同字段已有明确表达，却在传递或冷恢复时丢失：修传递和消费，不扩接口。
- 同一纯语义被复制到多个消费者且造成依赖环：先表征现有接受集，再下沉到已有合适的通用能力；业务授权仍留在 Cell。
- 信息展示与执行能力分开：ContextOS、prompt、UI 与 Job Token 不互相反向构造权威。
- 不把所有 owner 状态塞进一个可变的全局 context；按一次调用、一次决定保留必要的既有 typed 引用。

### 4.2 每条高风险交接只回答六件事

1. 事实由哪个 owner 产生，当前读取来自哪里。
2. workspace、Factory run、role run、task、attempt/session 分别属于哪个身份域。
3. 消费的版本、hash、receipt 或当前 capability 如何绑定。
4. 哪些字段必须保持，哪些转换由谁负责，什么叫冲突。
5. 何时真正产生副作用，重复、丢 ACK 和未知效果怎样处理。
6. 哪个测试能够同时证明非法拒绝与合法前进。

把这些填入已有合同文档或 verification card。它是工程审查内容，不新增一套运行态登记库或第二张任务表。

### 4.3 多 owner 一致性依靠各自原子提交和可验证引用

需要 CAS 的决定，应在**实际作决定的 owner 的原子 append/commit 边界**校验所需版本；在调用方预读 head、外面套锁或只检查 hash 非空，都不足以证明该决定没有竞争。

跨 owner 优先消费已有不可变 receipt/ref/hash/version；依赖可变条件时，明确失效、重评或补偿规则。它不等于跨 owner 原子事务，不新增中央总锁，也不承诺所有外部文件、进程和网络效果 exactly-once。

对外部效果未知的情况，先按原 attempt 对账；不能把“不知道有没有发生”当作“没发生”，再盲目重放。

### 4.4 保持不同生命周期可分别解释

至少分清：效果执行、持久收据/回合提交、任务/项目验收、资源结算。它们可以互相依赖，但不能压成一个 `success`。

例如，R10 记录的 `barrier closed / passed=false / release_allowed=true` 是安全失败后的有效收尾；不应变成验收通过。相反，产物已验证也不能自动说明未知 provider 或 lease 已经释放。

当前主工作区源码的一个正向边界是 `runtime.projection.public.service`：`query_project_outcome` 在 143—150 行明确只把 caller claims 变为 unbound candidate，不能签发 authoritative `completed_verified`；119—140 行另有读取 owner 事实的公开入口。设计应复用这种区分，实施前仍需定位实际消费路径及执行版本。

### 4.5 上下文追求足够与一致，不追求塞满窗口

当前任务、合同、CE 蓝图、目标文件、相关失败与工具规范按角色和任务依赖选择；控制权威继续通过现有 typed 合同和授权链传递。不要从 prompt 反解析权限，也不要让一次 retry 使用另一次调用的工具集合。

每次物理请求分别关联最终请求、实际工具面、快照与 transport 证据；历史参数未保存的部分继续 UNKNOWN。语义快照可读、某四次 wire 闭合与所有路线全覆盖，是不同结论。

### 4.6 观测与留存采用不同预算

实时 UI 发有界摘要与可读证据引用；原始审计由既有存储 owner 保留。读取工作集、单记录、单页、历史留存和总空间分别测量；不把增大一个 byte limit 当成寿命问题已经解决。

若确需分段、流式 strict 验证或索引重建，须保留原 hash/sequence、锁、fsync、损坏拒绝和冷恢复语义，并在原 owner 内迁移。是否需要结构调整，先由当前压力反例决定。

## 5. 什么时候修接口，什么时候重构

| 观察到的证据 | 选择 | 退出条件 |
| --- | --- | --- |
| 既有合同足够，某个 consumer 丢字段或另算默认值 | 修 producer/consumer | 真实交接与相邻正反例通过，不再扩大重构 |
| fixture 绕过正式构造器、缓存或 authority | 修测试/实验装配 | 原目标失败和合法对照都能触发；产品权限不改 |
| 原始事实正确，reducer/UI 解释错误 | 修派生投影 | 原件不变，热/冷与有失败证据的投影一致 |
| 多处拥有同一写权，或同一规则有冲突解释 | owner 内结构收敛 | 唯一写路径与完整 consumer 切换可证明 |
| 现有依赖环或协议形状让目标不变量无法表达/独立复现 | 有界模块重构 | 新旧语义对照、恢复与 policy 证据成立后切断旧路径 |
| 只有文件大、命名旧、测试多，尚无合同或维护成本证据 | 暂不据此重构 | 先测真实问题与改动成本 |

每次结构重构都应回答：将删除哪一套重复解释或旧消费路径。若只新增 wrapper、catalog 或状态字段，却没有减少既有歧义，应重新审查它的价值。

兼容退役以实际默认 consumer、持久历史、冷恢复、hash/版本兼容和替代验证为依据；不是“grep 不到”或同一投影自我比较。repair 迁移仍遵守既有 independent shadow 与 policy/revalidation 要求。

## 6. 实验怎样比过去更科学

### 6.1 保留四层证据，降低主要实验的随机性

| 层 | 使用什么 | 证明范围 |
| --- | --- | --- |
| L1 最小反例 | 真实合同、原 owner、确定性输入 | 目标机制能否重现与被推翻 |
| L2 真实接口链 | 正式 constructor/public producer、真实存储/工具/收据；必要时只替换远端 provider 为 loopback HTTP | 跨边界交接与恢复；不证明真实模型能力 |
| L3 候选集成与发布 | 风险相关回归、独审、既有 required ALL、精确源码/config 冻结 | 当前候选获得相应准入；不证明项目交付 |
| L4 正式原生任务 | 原合同、独立实例、正式 Factory 入口与只读观察 | 该候选、该任务、该干预条件的真实结果 |

冻结基线与候选应在独立私有目录/进程对照，不改正在执行的源码或目标项目。能够完整读取的历史调用才做原字节 replay；缺失旧 arguments 时，构造输入必须标成控制实验，不补写历史。

### 6.2 先验证测试本身

每个关键反例至少报告：

- 原版本确实进入目标 seam，并按目标错误码或实际错误效果失败。
- 注入点实际触发，不能因 fixture 提前报错而绿；适用时检查 `fault-fired == 1` 或同等独立哨兵。
- 修复后合法输入能前进，越权/过期/冲突输入仍在正确边界拒绝。
- 断言不只调用被测代码自己的判定；必要时核文件字节、canonical 事实、真实工具结果和独立读取。
- 暖对象、新 service、真正新进程分别标明；新对象不当冷启动。

### 6.3 最小实验菜单

以下按当前失败与风险选用，**不要求每个改动执行全部实验**；现有强制门禁仍按仓库要求执行。

| 实验 | 操作/扰动 | 独立观察 | 必须区分的结果 |
| --- | --- | --- | --- |
| E1 工具面与权限 | 完整 native 清单、alias/wrapper、空权限、越界成员 | offered schema、callback 清单、每成员结果、实际文件 | 合法未丢失；非法明确拒绝；上下文不扩权 |
| E2 冷重建等价性 | 持久提交后 compact heartbeat，再读暖对象/新 service/新进程 | canonical 字节、owner/session/subject、消费者判断 | 相同事实同义；损坏/缺失明确失败或 UNKNOWN |
| E3 重复与 ACK 丢失 | 普通 replay、提交已落盘但 ACK 丢失 | durable claim 数、grant、真实效果、nonce 对账 | 普通重放不重新授权；本调用恢复不新建效果 |
| E4 CAS 与 owner 竞争 | 在实际 append seam 控制竞争顺序，插入新失败/新版本 | 最终 canonical 事件序列与决定绑定 | stale 决定不得越过新事实；不靠预读证明 CAS |
| E5 效果后的异常 | 工具执行后、receipt 前后、outcome 前后注入异常/进程终止 | 字节/进程事实、原 receipt、重启恢复 | 未发生、已发生、未知分别保留；未知不盲重放 |
| E6 取消与资源 | provider 超时、工具在途、suspended/cancel、lease 过期 | transport terminal、session、barrier、lease、独立端口 | 逻辑取消不冒充物理排空；失败也可合法释放 |
| E7 QA 与验收当前性 | 新旧 Director epoch、当前输入改变、failed/missing/NOT_RUN 组合 | 对应 run/epoch/input 的 verifier 与 QA 原件 | 历史结果不覆盖当前；证据存在失败不变 missing |
| E8 合法修复的活性 | 可修复反馈、空 final、本轮无新 batch、预算边界 | 原 owner commit、后续真实请求与复测 | 有依据才继续；无进展或非修复失败明确停止 |
| E9 容量与观测 | 合法长历史、大内容引用、事件重放、WS 摘要 | 峰值内存、I/O、保序/hash、UI 绑定、可读引用 | 正确性不丢；读取预算与历史寿命不混同 |

E5 若没有可对账的效果证据，正确结果可能是保持 UNKNOWN 并阻止自动重复效果，不能为了恢复率强造成功。此类样本应归入安全对账/活性待完善，不记成已自动恢复。

### 6.4 生成状态序列，避免只修已知样例

对已有稳定 owner 合同，可从最短反例扩展到“claim、execute、receipt、ACK-loss、resume、cancel、重启、query”的合法与非法序列。参考模型仅存在于测试层，用于检查不变量；生产状态仍由原 owner 持有。

Hypothesis 的 stateful testing 可生成操作序列并给出缩减后的失败程序；这是可选的测试工具，不是生产依赖，也不自动验证真实并发。并发问题仍需可控调度、真实多进程或必要的有限状态建模。[官方说明](https://hypothesis.readthedocs.io/en/latest/stateful.html)

保留未参与修复的组合/项目作为留出样本；原 L1-L12 量具、合同、预算和分母不因训练或修复成绩改变。新增质量政策单独版本化。

## 7. 让研究有结束条件

每个研究 topic 复用既有记录，仅固定八项：问题、真实 owner、版本基线、一个假设、推翻条件、实验与预算、相关回归/独审、当前结论与下一动作。

| 结果 | 下一动作 |
| --- | --- |
| 原机制 RED、改动后 GREEN、合法/非法对照与相邻消费者满足既定范围 | 结束该机制研究，集成并按既有门禁冻结候选 |
| 原机制不能重现，或故障哨兵没有触发 | 修实验或标证据不足，不据此改产品 |
| 单个接口修复被新反例推翻 | 更新同一 topic 假设；必要时扩到已证实相关的 owner/消费者 |
| 新风险只是静态猜测，与当前边界无因果关系 | 记录后续研究项，不自动变本次前置 |
| 有越权、重复效果风险、伪造接受、跨 workspace 或当前候选完整性失败的直接证据 | 阻止该候选进入下一实际执行，回到对应 owner；不放宽门禁 |
| 达到本实验预先声明的资源预算 | 输出支持/推翻/证据不足，决定下一有限实验；不假装问题已修 |

“实验结束”不等于“项目完成”。项目目标继续推进；用有结论的小实验替代没有边界的持续研究。已有要求的门禁不减少，也不因每次遇到新疑问就扩成无止境的全平台重审。

## 8. 实施顺序：五阶段，每次只推进当前一条

### 阶段 A：先收尾当前正式样本

本次读取的 `current-phase.json`，`at=2026-10-20T07:41:36.906948Z`，嵌套 `r11_native` 记载 `factory_435e574ec4aa` 已在冻结隔离源码运行，QA 尚未观察、ProjectOutcome UNKNOWN、资源 ACTIVE；旧的 phase/admission/candidate 字段仍记未准入。

这证明工程档案存在新旧描述并存，不证明真实运行越权，也不是本次的 live owner 验收。应按 exact-run 的正式准入、原始执行与 owner 证据核对；本方案不据旧字段启动另一轮竞争运行，也不对在途候选改源码/config/model/目标产物。

产出：该运行的交付、QA、Outcome、效果、资源各自终态与第一失败；缺证据保留 UNKNOWN。当前动作按该次 operator 的既有控制协议继续，不由本设计发取消或重启动作。

### 阶段 B：只关闭第一有效失败边界

从 A 的结果选一个真正阻止继续的机制；若 A 成功，则选一个实际暴露的恢复或成本风险，不继续按旧错误清单盲修。完成最小反例与对应接口/投影/fixture 修正，必要时才局部重构。

产出：已有 verification card 的闭环、真实相邻消费者结果、有限独审与退役清单。其他 owner 可以并行只读研究；默认同时一个写入 topic，写范围互斥。

### 阶段 C：集成、冻结、正式新验收

达到 B 的退出条件后结束研究，完成 required 回归/独审/发布门禁，冻结实际执行源码/config/合同，唯一 operator 启动一个新的正式隔离样本。

对零外部修复验收，沿用原始 catalog 合同和正式 Factory HTTP；观察器不预置需求/catalog、不初始化目标 Git、不补装依赖、不代跑验收、不写 receipt/ledger。完整运行预算保留既有要求，不把短启动 smoke 计为交付样本。

产出：C 的真实成功或第一失败。失败回 B；不把后续源码修复追溯到旧运行，也不在一轮中跨多个无关 owner 追补。

### 阶段 D：证明重复性与受控恢复

固定候选、合同/项目集合、模型路由、预算和干预政策，再做预先声明的重复与故障样本。受控注入、正常交付、工程协助恢复分别分组；同 run 多次 retry 不当多个独立 batch。

产出：明确分母、样本量、失败谱系、恢复结果与成本原值。连续几次通过只提供有限重复证据，不宣称通用可靠性或稳定 SLA。

### 阶段 E：以结果决定扩域、简化与进一步重构

按瓶颈选择下一语言、任务类型、并发或长期运行维度。先检查现有 language slot/catalog/coverage；不以规则条数或语言名录代替可执行与真实验收。

只有“重复维护与故障成本”以及“迁移后的收益”有证据时，才退役兼容、合并重复测试或扩大结构重构。保留独立防线；仅因两项测试都通过，不足以认定其中一项冗余。

## 9. 用什么判断正在收敛

运行到达更后阶段、同一测试从两错换成另外两错，都需要解释具体证据；不能只看数量。建议同时记录三类变化：

1. **结构变化**：同一语义的独立实现、隐式默认、旁路和不必要 consumer 解释是否减少；没有把歧义搬到新 wrapper。
2. **机制变化**：目标最小反例消失，原合法/非法对照仍成立，冷恢复与必要竞争反例没有退化；前后诊断身份可核对。
3. **真实效果**：同条件下正式交付、恢复、端到端时长和可核成本有没有改善；扩大项目域时单独报告新分布。

### 最少指标与分母

| 指标 | 分母/口径 | 缺失时怎么写 |
| --- | --- | --- |
| 正式任务交付率 | 固定候选全部已启动正式样本；平台与环境失败均保留，未结束样本单列；准入拒绝另列漏斗 | 不把未结束记成功或失败，不排除失败美化分母 |
| 合法恢复率与安全终结率 | 预先定义的 eligible 故障机会；注入与自然事故分别报 | 需要对账但效果未知：UNKNOWN，不计自动恢复 |
| 非法效果/重复授权/伪造接受 | 与具体反例及实际执行机会对应；零事件保留样本范围 | 零观察不证明零风险 |
| 延迟与开销 | 每次全链及分阶段原值，含失败/结算时间；少量样本不宣传 p95/SLA | 排队、模型、验证、观察无法分解时标未知 |
| 物理模型开销 | 全部 transport 尝试、重试/取消、真实 token/cache usage、可核账单，按 attempt 去重 | reported usage 与价格估算、实际账单分列 |
| 工程与观测成本 | 实际研发、操作、审核、观察分钟，外部 Agent、I/O/存储与归档成本 | 无记录是 UNKNOWN；等待墙钟不等于人工分钟 |
| 单个成功交付总成本 | 全部尝试的已知成本加可归属工程/迁移摊销，再除成功数 | 成功数为 0 时未定义；缺项不补零 |

成本比较应固定质量、安全、任务分布、模型和预算。减少模型调用却增加人工修复，不算已经改善无人值守经济性。多个不同版本的历史成功不合并计算当前可靠性。

## 10. 独立验收要怎样避免共同犯错

PM 合同、CE 蓝图、Director 产物和 QA 若都从同一错误解释推导，内部一致仍可能交付错误。要保留来自原始用户要求的行为义务、固定入口和留出测试；verifier/QA 的独立证据不能由被验收方的自述直接生成。

端到端原则说明，仅在底层实现局部检查不足以替代应用端的完整验证。本方案将其用于 Polaris 的推论是：文件 hash、receipt、状态闭合都很重要，但最后仍须执行用户实际需要的入口和行为义务。[原始论文](https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf)

重试的设计应以稳定请求意图和明确幂等语义为基础，并处理相同标识但不同参数的冲突。AWS 对幂等 API 的论述支持这一方向；在 Polaris 中仍须按真实效果边界逐项证明，不能借此宣称外部效果普遍 exactly-once。[原始工程说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 11. 方案的边界与实施者可以自行决定的事项
