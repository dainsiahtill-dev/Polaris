# 工程上下文事实与引用的收敛

## 边界和数据流

仓库的 CLI、HTTP、Electron 与浏览器工作台均由现有工程服务驱动。收敛围绕一次工程运行展开。宿主负责记录事实、选择可取回的版本和执行授权，Director 与 QA 使用这些事实做各自的判断。

```text
EngineeringRunService → sessions.sqlite3 → 当前运行截至请求时的工具观察
                                         ├─ 文件事实摘要 → Director / QA → provider request
                                         └─ manifest → ContextOS
read_file(content_ref, 行范围) → 当前运行的读取绑定 → workspace 内 FileCard 快照
物理请求捕获 → 已落盘的 context_snapshot_ref → runtime.v2 → 工作台快照查看器
```

## 可验证的收敛点

1. 统一前端请求快照的识别和可用状态。工程控制台、讨论、工作台、导航图与弹窗从同一处消费；保留日志输入的大小写归一化。文件卡、命令回执和事件号可以展示，打开请求须有已落盘的请求快照和原角色。
2. 将工程事实的解释留在 `roles.runtime`。每次按当前 run 的工具回执和顺序派生 path、完整版本、符号、结构与可核查的验证绑定。请求与 manifest 共用该解释。消除按文件名排序取“最新版”和逐请求遍历工作区快照目录的路径。
3. 文件正文只落在既有 FileCard 存储。模型获得有限条完整摘要和内容地址；需要细节时可按同一地址及行范围取回。命令写入、源码变更、引用缺失、调用失败和未验证候选必须保留其不确定性。QA 对产物独立取证。

## 验证和实施顺序

全仓 AST 清点还发现 Director 的旧兼容入口复制了规划规则、源码上下文收集和整个角色类。两组收集函数和规则函数的定义逐个相同；execution 的角色实现另有任务耗时、风险和完成计数。规则与上下文收集归已有 planning Cell，execution 经已声明的 planning 依赖复用角色实现并保留计量。保留旧 import 路径，用两侧的公开服务、相同输入、风险持久化、QA 记录与计量回归核对。新工程仍由 EngineeringRunService 驱动。

先验证 UI 中可打开的地址、不可打开的内容引用、无效或缺失状态、原始角色。再用带多个版本、同内容不同路径、写后失效、折叠和独立 QA 的日志验证摘要与取回。检查最终请求中的精确引用以及 manifest 对该请求的解释。源码变更期间保持 Bench 静止，检查 Ruff、mypy、pytest、前端类型与回归，随后逐项目运行。

历史同项目基准为 L1-05 重读 40/50、L1-06 重读 14/45。每项实验记录项目、运行、源码指纹、reads、rereads、显式快照取回、QA 工具轮次和最终裁决。预定目标为 L1-05 重读率低于 20%。全量独立验收以 120 项目录的真实运行记录为准。

## 第一份候选的实跑证据

候选 `d6ce251dfd29f517` 的 L1-05 批次为 `bfc5007432f5428389c6bc275f47ae6e`。Director 快照 `82669baf8ed900c4720afdf0` 的物理消息包含一条可寻址摘要；按请求截止事件 370 重建的 manifest 命中同一条。

首个显式取回尝试出现在工具事件 488。快照 `f0d5a566d2ef8baa68612a18` 的实际 schema 仅有一个 `anyOf` 分支，该分支同时要求 `file` 与 `content_ref`。新路径第一次读取时还没有内容地址。模型提供了一个未签发的 65 位值，事件 489 记录失败。注册表运行时按“每组至少提供一项”校验，生成 JSON Schema 时也须保留这个逻辑。下一候选需分别验证只有路径、只有已签发引用、两者匹配、两者冲突、两者都缺。授权和快照内容核验仍在执行侧。

历史 L1-05 的 15 个路径中，旧目录排序对 4 个选到了错误版本。按相同终点的日志回放，新索引覆盖 15 个路径，版本错配为 0，其中 14 个有匹配的候选验证绑定。运行时重读计数同时保留原审计脚本的“路径曾被折叠”口径和按时间顺序的同路径同 SHA 计数。

同项目最终对照采用基线 `5660dd0f40cd410f8cd6ddd2f5d47af3` 和候选 `bfc5007432f5428389c6bc275f47ae6e`。候选的功能、fidelity、独立 QA 与 Bench 均通过。按原审计口径，重读由 40/50（80%）降为 11/37（29.7%）；同路径同 SHA 的重复实读由 24 降至 8，成功快照取回由 0 增至 4。QA 由 44 轮降至 27 轮，浏览器观察由 8 次降至 7 次。该对照覆盖一组共同启用的改动，暂未达到低于 20% 的既定目标。

随后的注册表修正将“每组至少一项”正确投影为 JSON Schema。184 种字段组合的对照中，不一致的工具从 3 个降为 0。多实验室试验的真实原生请求也记录到 `read_file` 的两个可选分支。新版的 L1-05 重读率仍需在新的完整项目运行中测量。
