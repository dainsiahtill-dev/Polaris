Polaris 将模型决策、工具效果、运行状态、上下文和验收证据分开，再通过执行身份与公开契约把它们连接起来。理解底座的关键是：谁拥有事实，哪一步真正产生副作用，哪一种完成能被下一层消费。

## 两条相互连接的路径

执行路径由 PM 的任务合同、CE 的蓝图与 handoff、Director 的工具执行及修复、Verifier 与 QA 的验收组成。模型可以提出方案与调用，但文件、进程、权限及验收状态由确定性实现控制。

上下文路径把会话与状态提取为当前角色的输入，加入合同、蓝图、目标文件、失败反馈与工具规范，再经过窗口预算和 provider 协议转换。上下文投影说明模型可能看到什么；最终 wire 审计才说明受治理发送路径实际发送了什么。

## 必须区分的四类对象

| 对象 | 回答的问题 | 示例 |
| --- | --- | --- |
| 事实 | 什么真实发生，谁负责 | owner event、DEO commit、进程终态 |
| 投影 | 当前如何理解多个事实 | TaskBoundary、Run Ledger、ContextOS UI |
| 缓存或引用 | 如何避免重复搬运内容 | ContentStore、ReceiptStore、大文本指针 |
| 权限 | 当前可以做什么 | 合同派生 JobToken、fresh claim、一次 fence |

投影可以重建，缓存可以过期，权限可以失效。它们与事实相连，但不能互相替代。

## 至少六种完成

一次模型请求结束、一次效果收据提交、一轮内存状态完成、任务完成、Factory 编排结束与 ProjectOutcome 接受，分别回答不同问题。TransactionTurn 的内存 COMPLETED 早于持久 OutcomeCommit；项目接受需要当前多个 owner 的证据。失败的运行可以安全释放资源，但不会因此变成验收通过。
