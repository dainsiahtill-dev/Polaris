# 如果由我重构 Polaris 底座：面向无人值守自动化开发的具体决策

日期：2026-09-30。状态：设计建议，未实施。适用基线：`0d475c60474f2b1ea4a06ea136c0f817d2c49bfa`。

用户最终目标：**无人值守自动化开发**。工程师可以输入需求、授权范围和预算；平台在这些边界内自行构建、发现问题、修复、验证、恢复和交付，不需要人反复盯日志、挑修复文件、清 runtime 或从 PM 重启。

本篇回答“优先重构哪部分、如何切换、验收什么”。完整历史、证据和任务包见[总方案](POLARIS_UNATTENDED_DEVELOPMENT_MASTER_PLAN_20260930.md)及[执行计划](../../../../docs/superpowers/plans/2026-09-30-polaris-unattended-development.md)。

## 1. 我的第一选择：执行与恢复闭环

我会先把 **Factory/Director/workflow 之间分散的修复决策、预算、状态保存与续跑逻辑收敛**。这是最接近用户痛点的底层改造：已经成功生成了一部分代码，发现一处错误后，平台应像工程师一样修当前问题并继续，而不是结束、丢位置、重复读旧诊断或重建全部项目。

“执行与恢复内核”是职责名称，不表示新建另一个大 Engine 类。实现应拆在现有 owner 内：

- `director.runtime`：局部诊断、候选计划、因果进度、修复策略。
- `orchestration.workflow_runtime`：项目/阶段恢复 cursor、累计预算、等待/继续/停止决定。
- `factory.pipeline`：调用 owner、推进实际阶段、持久化自己拥有的 stage/chain 事实。
- `runtime.task_runtime`：claim/lease/fence、DEO durable receipts、recovery 和 parent close。
- `runtime.execution_broker`：项目 artifact/verifier/process 物理证据。
- `runtime.projection`：从 owner 事实聚合唯一最终结果。

我不会把这些合并成一个跨 Cell 超级服务；要减少的是重复决策与隐式状态，不是抹掉已经合理的权威边界。

## 2. 为什么优先这里

历史表明，Polaris 多次已经具备写代码、调用工具、生成蓝图、运行编译与入口的能力。主要问题集中在“失败后下一步怎么办”和“成功事实怎么登记、什么时候仍然有效”。

L3-24 r92 给出具体案例：PM/CE/Director 成功，编译和 CMake 通过，最后修复轮确实有 edit、候选接受、诊断从12降到3，但 QA 仍有两项行为错误及深度不足，且停止原因为空。代码允许基础8轮加最多2轮扩展；不能仅凭10轮判断失控，也不能认为再加几轮一定成功。

这个案例最需要的不是继续给模型强调“你一定要修好”，而是一个可重放的决定：本轮为何退出、哪些成果已保存、剩余失败归谁、现有预算是否允许继续、下一次进程启动从哪里恢复。

## 3. 重构优先级

| 优先级 | 重构/验证对象 | 具体目的 | 主要任务包 |
|---|---|---|---|
| 先验安全 | claim replay、effect recovery、释放 barrier、多 owner outcome切面 | 证明不会重复写、丢 effect、用旧证据假绿 | P02/P04 |
| 第一刀 | 分散的修复与恢复状态 | 失败可续、进展可保存、预算可解释 | P01/P03/P07 |
| 第二刀 | 跨层诊断与验证结果 | 准确找到当前失败，区分失败/缺失/skip | P08a/P02/P14 |
| 第三刀 | CE/Director 的可执行交接与修复上下文 | 减少先天不可执行合同和无效编辑 | P05/P06 |
| 第四刀 | 运行身份、投影和观测负载 | 长时间运行不被 UI/全扫描/目录重建拖垮 | P09 |
| 后续扩展 | 语言能力与产品调度政策 | 在稳定内核上扩展，不按语言复制流程 | P10/P11/P12/P13 |

安全先验与第一刀的只读调查可并行。发现真实权限/重复 effect 缺陷时，先关该漏洞再跑 live。没有动态证据证明缺陷的模块只补反证测试，不为了统一架构强行重写。

## 4. 第一刀具体怎么拆

### 4.1 当前循环拆成四个可独立测试部分

1. **事实输入适配器**：只从 public owner 获取当前 scope、contract、候选、verifier和预算；保持原始来源与身份。
2. **纯决策函数**：根据同一组 typed evidence 输出 continue/revalidate/repair/wait/stop，不读磁盘、不调模型、不写任务状态。
3. **受控动作执行器**：走现有 claim、工具、DEO、broker，不复制权限判断；只执行决策中允许的动作。
4. **持久化恢复位置**：保存动作身份、完成 ack、下一位置、预算消费；事实本体通过引用回查 owner。

先抽出可证明等价的纯策略，再逐个接 consumer。Factory 的阶段编排继续存在，不能一次删掉所有保护分支。新旧路径在迁移期仅可单 writer，shadow 仅读取与比较决定。

### 4.2 每一次修复成为显式事务

输入必须绑定：

- 哪个 run/task/attempt/delivery epoch；
- 哪个 PM/CE/completion contract 与 policy version；
- 当前哪项 verifier/behavior obligation 失败；
- baseline 文件 hashes 与可写 scope；
- 需要阅读但不可写的 sibling/test context；
- 本轮预算、已消费总预算及必须重跑的 verifier。

执行结果不能只有 `ok`。必须能解释：未执行、授权拒绝、无变化、已执行待结算、候选被接受、候选被拒绝并已回滚、回滚失败待隔离、验证失败、预算退出、完整通过。

这些概念尽量映射现有 DTO；确需扩展时在单 owner 做有版本的字段/枚举变更，先有契约与负例测试再接消费者。

### 4.3 单轮结束不等于项目丢失

进展存在但本轮预算用尽，应落盘 accepted checkpoint 与当前 residual。是否自动继续由用户既有项目预算和 policy 决定；允许继续时创建新合法 attempt、继承累计计数，不能重置所有额度。

普通编译/行为失败留在 Director；QA失效只重跑相关验证。仅当合同本身确有矛盾、需要新授权或新增接口时，才请求 CE/PM 产生最小变更并失效受影响子图。

### 4.4 第一刀的最小交付

- r92 的每条可能退出路径都有明确 stop_reason。
- 最后有效 edit/receipt 不会因 round结束丢失。
- 重启进程后能恢复同一个失败 owner，PM/CE 物理调用次数不增加。
- 对同一失败重复无效编辑触发有证据的停止；不同 owner不能洗掉累计预算。
- 终态仍红时保留确切残差；不把 checkpoint存在当交付成功。

这五条过完再扩大改动范围。它们比再加几十个语言规则更直接检验无人值守能力。

## 5. 第二刀：用同一套诊断驱动修复和解释

用户界面、QA、修复器、模块归因不能分别从不同 tail/关键词猜原因。复用 `audit.diagnosis` 和 verifier DTO，以同一个失败事实构建不同用途的派生视图。

每条失败需稳定身份、命令与测试清单、baseline/candidate hashes、完整输出引用、expected/actual、因果源文件、owner与可信度。诊断不是权限；进入写入前仍需要当前 JobToken/lease/scope。

P08a 必须早于复杂收敛重构。否则“progress”建立在重复截断的日志上，后面再复杂的 scheduler 也会错。r92 的 domain shim skip 特别需要校正：真实编译失败不能被伪装成工具链不可用，required skip 不能 PASS。

跨语言使用 typed adapter：C++编译器/Node TAP/Python unittest/Rust/Go/JVM 各自映射稳定结果，平台通用层不理解“隐形日记”“月相”业务语义。测试逻辑错误仍由 Director基于合同修代码。

## 6. 第三刀：把交接变成能执行的合同

CE 不是额外自然语言审批关卡；它必须交付 Director 可以执行的任务图和完成义务。至少明确 artifacts、owned paths、public API、依赖、入口、verifier和验收政策；同一个字段不能在 PM、CE、adapter 各有不同解释。

当前 CE 已有 candidate/patch/receipt 和局部 schema恢复，应在它们上面补：

- 同时报告彼此可兼容的结构缺陷，减少每次只修一个字段。
- required fields 的 Provider schema 与 typed constructor 同源或有等价性门禁。
- 归一化合法输入不变、幂等、无权限扩大；冲突保持fail-closed。
- 最终请求包含当前任务所需工具与失败上下文，不因 slim/retry丢失。
- 相同失败在同 owner 的编辑请求中恢复，而非强迫 CE重写全部设计。

PM若当前只是合法 deterministic contract加route probe，短确认句不能当作失败。角色是否合理取决于当前任务模式和最终契约，不取决于回复字数。

## 7. 安全底座怎么验证，不怎么“简化”

三个高风险项来自当前静态代码/测试矛盾，还没动态证明：exact claim replay grant、terminal release 的 open effect、outcome多owner读取切面。

正确重构方法是把反证写到真实边界：

```text
两个进程竞争同 operation
持久化成功但 ACK 丢失
effect 发生后进程崩溃
receipt已提交但投影还没更新
QA 通过后另一合法 attempt 修改文件
租约释放后旧 worker 发来结果
```

要同时证明安全和可恢复：一次操作不重复副作用；失败能安全释放；未确定结果不会假成功；已成功的effect不会因投影缺失重做。

不能为减少门禁删掉 scope/fence/hash；也不能为“fail-closed”让一切普通错误都永久封死。每个 hard block 必须有责任层、证据、恢复条件。安全拒绝正确、恢复机制缺失也同样是需要修的平台问题。

## 8. 模块化的正确尺度

我赞成彻底明确职责，但不赞成按每种错误或每个函数做独立模块。合适的单位是一个可独立演进的契约及其状态 owner。

每个模块具有：public contract、private implementation、effect ports、state owner、invariants、有限 failure taxonomy、独立 gate、依赖影响图、版本和已验证证据。

稳定模块无需反复修改，但也不是永久免验。只在真实破坏其不变量或接口变更时解封，重跑相关依赖闭包。把大文件拆成十个 mixin却仍共享隐式可变状态，不算完成模块化。

当前不优先微服务化、不优先更换数据库、不优先重写所有prompt、不优先更换全部模型。只有动态 profile/故障注入证明既有机制无法满足要求时，才开对应结构迁移包。

## 9. 软件开发与游戏开发共用什么、专用什么

共用底座：需求合同、文件/命令工具、权限、恢复、receipt、依赖图、验证、成本、审计、终态。

专用 adapter：语言编译器/包管理器、引擎/平台、交互入口、资源构建、运行环境和验证方式。每个adapter声明可用能力和可证明的成功条件，不复制一套PM/CE/Director执行引擎。

“任何语言”意味着允许新增满足协议的工具链，而不是必须先编写所有语言的确定性语义修复。真正的语义实现由模型和现有工具完成，平台确保上下文、权限、反馈与迭代可靠。

## 10. 怎样才算达到无人值守

建议首先证明以下四种场景，在固定平台版本下不需要工程 Agent中途补代码/改状态：

1. 新项目从需求到真实入口和全部必需验证通过。
2. 项目首次编译/测试失败，平台自动定位、edit、复测并完成。
3. 执行中进程退出或连接断开，平台安全恢复原阶段并完成；没有重复不可逆副作用。
4. 遇到超预算/权限矛盾/工具链不可用，平台保全已完成工作并输出明确可恢复阻塞，不假绿、不无限耗费。

第四项不是“交付成功”，但属于无人值守系统必须具备的可靠失败能力。平台整体目标仍是提高前三项在明确能力矩阵上的成功率。

首个项目证明闭环；固定canary证明代表性；N-batch证明有限矩阵中的重复稳定性。主 Agent现场修平台后恢复成功属于工程协助结果，必须单独统计。

## 11. 什么不会被写成承诺

- 不能根据15个工作包估计“15个bug修完就全部成功”。工作包含验证和治理，不全是已证缺陷。
- 不承诺任何模型在所有需求上必然成功；模型质量需要在上下文/工具/预算完整且底座无阻塞的条件下评估。
- 不承诺先重构数月再验收；每个切片都能独立运行和反证，第一轮就应带来更明确的停止与恢复证据。
- 不把已有历史项目成果归零；也不把历史绿复制成当前版本资格。

## 12. 我会从哪里开始

先完成当前源码、graph、模块门禁和历史档案的基线校准；随后并行只读验证安全H1～H3和r92退出链路。写入阶段一次一个排他桶。

若安全反证通过，第一桶实现“明确停止决定＋持久恢复位置＋同阶段续跑”，第二桶统一verifier诊断与失效语义，第三桶收敛Director候选调度。若安全反证发现真实漏洞，则先修它，再继续第一桶。

每个桶都以真实handler/fault injection、模块门禁和同阶段恢复结束；固定候选版本后才做fresh无干预证明。最终选择方向的指标始终是：**是否让项目在没有人接管的情况下继续推进并交付，而不是代码是否变得更复杂或测试数量是否更多。**
