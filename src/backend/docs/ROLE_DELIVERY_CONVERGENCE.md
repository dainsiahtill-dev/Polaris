# Role delivery convergence

The production task chain remains PM → Chief Engineer → Director, followed by
independent QA. All role execution uses the existing RoleExecutionKernel and
roles.runtime session host. Planning contracts and observations do not grant
effects or prove delivery.

## Product intent and technical ownership

PM emits `pm.task_intent.v1`: product goal, required and optional requirements,
observable acceptance, explicit constraints and a dependency graph of tasks.
One coupled implementation task is valid. PM need not guess file names,
generated output graphs, implementation steps or verifier argv before the
repository exists. Explicit typed paths and commands remain exact constraints.

The public PM admission gate validates intent and the dependency graph. Draft
omissions receive correction feedback. Unsafe explicit paths remain rejected.
Legacy task contracts retain their existing typed technical authority.

Chief Engineer receives the committed product intent and establishes exact safe
artifact ownership and executable verification recipes before Director receives
an execution capability. CE recipes are classified through control-plane
verifier policy, bound into the completion contract and revalidated against
actual files and executables at execution. Existing explicit command bindings
cannot be silently omitted, rewritten or transferred to another task.

CE plans need only be sufficient to begin. Shared interface and behavior
contracts are required where separate owners depend on them; a single coupled
task can use empty declarations and invariants. Architecture, interface,
ownership or authorized-scope changes need a new CE handoff. Ordinary local
compiler, test, missing-file and stale-edit failures remain Director work.

## Persistent execution and completion

Director receives task-needed read, search, edit, write and command tools under
the existing policy. Default execution is continuous. Write-only first-call
bootstrap and single-batch behavior require explicit configuration.

The same task session retains its goal, CE handoff, committed observations and
latest failure feedback. Successful writes lead to verification; failed
verification leads to a local repair and fresh verification. Earlier turn
effects can satisfy cumulative obligations only through authenticated committed
facts, never through provider text, transcript JSON or a replayed receipt claim.

Budgeted sessions use their enclosing deadline and cancellation boundary rather
than an implicit ten-turn cutoff. Explicit caller turn limits remain enforced;
unbudgeted sessions retain their legacy limit. Workspace scope, execution
authority, cancellation, physical process drain and authentic receipts remain
hard boundaries.

QA reads the exact same-run CE artifact targets when PM delegates topology.
Physical workspace verification and same-owner recovery retain failed evidence
until a real rerun passes. Task/session status, model prose and test-component
success cannot substitute for current artifact, command, entrypoint, QA and
settlement evidence.

Bench is an internal consumer of these platform contracts. It does not own the
role semantics, execution capability or completion truth.


### PM bounded product advice admission (2026-10-13)

`pm.task_intent.v1` has a strict required semantic core. Product metadata, recipe suggestions, complementary scope prose, and novel JSON product facts survive in a bounded nonauthoritative planning advisory namespace. The aggregate bound is 65536 UTF-8 bytes, 4096 JSON value nodes, and depth 8. Direct role/routing/execution/job/identity/protocol/typed capability fields reject; nested advice does not promote acceptance, constraints, trusted catalog depth, run binding, paths, commands, or grants. Optional typed technical fields remain exact and fail closed, including illegal root `.` paths; correction feedback suggests only technical fields explicitly declared in the original requirement.

Task-purpose governance detection covers title, goal, description, and local acceptance; preserved global requirements may mention CE/Director product coverage without turning the implementation task into a governance task. Prompt-leakage checks still cover all semantic product fields. These source and HTTP admission checks are component evidence; fresh native execution, QA, Run Ledger, real entrypoint, and terminal release remain separate required acceptance.
